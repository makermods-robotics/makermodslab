# S3.7b as built (2026-09-03) — MolmoAct2 over DRTC, the frontend half

The other half of S3.7a. The backend already reported everything the panel
needed (`supports_rtc`, `requires_task`, `n_action_steps`, `chunk_size`); this
slice is what makes the panel READ it, plus the one control that was missing
entirely — a way to answer "which of this robot's cameras plays the checkpoint's
`cam0`?".

Frontend only. No Python was touched, no route was added, no ratchet moved, and
no dependency was added.

## The problem, exactly

`lerobot/MolmoAct2-SO100_101-LeRobot` names its cameras `cam0` and `cam1`. The
Deploy panel binds a checkpoint's cameras to the robot's **by name only**
(`cameraBindings`), so both roles landed in `unmatchedCameras`, `allCamerasReady`
was false, and Start was blocked with a message telling the operator to *rename a
camera in Robot settings*. There was no other route: the checkpoint was startable
only by hand, from the generated `modal run` line.

## The design decision this is built on

Locked before implementation, and the reason the storage looks the way it does:

> A camera's **name in the robot record is its identity**, and is never renamed
> to suit a checkpoint. A checkpoint's camera name is a **role**, bound per run.

Consequences that show up all over the diff:

- name-match stays the default and gets **no control at all** — a dropdown whose
  only correct answer is already selected is just a chance to get it wrong;
- only unmatched roles get a picker, so the ordinary run sees nothing new;
- the pick is remembered per (checkpoint, robot) in `localStorage`, **never**
  written to the robot record;
- the picker changes only what the START REQUEST says. The server still resolves
  the device from the robot record **by name**, exactly as it did for a
  name-matched binding. Nothing in the UI claims otherwise.

## 1 · The camera role picker (remote runs only)

New `frontend/src/components/remote-inference/CameraRoleBindings.tsx` —
presentation only: it takes slots, options and an `onChange`, and knows nothing
about run modes, storage or binding derivation. It renders `null` when the slot
list is empty, so a checkpoint whose cameras all match by name is exactly as it
was. Structured this way so the LOCAL rollout can adopt it unchanged if it ever
wants the same escape hatch; **only the remote run is wired to it today.**

Mounted in `RemoteInferenceBlock` between `RemoteRunFields` and
`GpuLaunchSection` — the roles are part of what the run sends, and the command
below is generated from a configured run.

`DeployPanel` derives the rest:

- `remoteCameraBindings` — `cameraBindings` with the picks layered **over** it.
  A name match always wins (the map is only consulted for `camera == null`), so
  the local list is untouched, identity included: with nothing picked,
  `remoteCameraBindings` is `cameraBindings`.
- `bindingsFor(mode)` — which list a verb reads. `handleStart` uses
  `bindingsFor(mode)` (the LAUNCHED mode, not the armed one — the verb row can
  launch a mode it has just armed), so the local start payload is byte-identical
  to before.
- `remoteUnmatchedCameras` / `remoteDisconnectedCameras` /
  `remoteMismatchedCameras` — the same three questions asked of the remote list,
  kept **beside** their name-only twins rather than replacing them.
- `camerasReadyFor(mode)` — feeds `deployGuards`' `allCamerasBound` and
  `canStartAnyMode`. **`deployGuards.ts` was not changed**: its semantics are
  still "every camera the checkpoint expects is bound to a device", and only the
  caller's computation of that fact became mode-dependent. `remoteCamerasReady`
  is never *less* ready than `allCamerasReady` (picks only add bindings), so no
  verb can be blocked by this that was not blocked before.
- `camera_dims` is unchanged in kind: it still comes from the CHECKPOINT's
  `image_features`, the same for a picked role as for a name-matched one.

Disconnection is judged for a picked camera the same way it is for a matched one
(`isCameraConnected` against the live enumeration): **a pick of an unplugged
camera is a pick, not a binding**, and still blocks Start.

The unmatched-camera alert gained a remote-only sentence
(`studio.deploy.cameras.unmatchedRemote`), because "rename one in Robot settings"
is now the wrong remedy for a remote run — the picker above it is the answer.

### Storage key shape

`frontend/src/hooks/useRemoteCameraRoles.ts`, following `useSelectedModel` /
`cameraPrefs` (every read and write wrapped in try/catch; an unavailable store
costs the memory, never the run).

```
localStorage["makermodslab.remoteCameraRoles"] = {
  "<policyConfigJobId ?? '-'>::<checkpointRef>": {
    "<robotName>": { "<roleRequestKey>": "<robotCameraName>" }
  }
}
```

- The checkpoint half is `remoteCameraRoleKey(policyConfigJobId, selectedRef)` —
  the pair the panel already uses to address `/policy-config` (`(owner_job_id,
  step)` is unique where `(tip, step)` is not, and `ref` is the checkpoint's true
  identity).
- The robot half is the record's `name`, because "which camera is the wrist one"
  is a per-robot fact.
- **Validated on read, not on write.** A remembered pick naming a camera the
  robot no longer has is dropped silently (the hook filters against the record's
  current camera names on every render), so a delimiter collision in the
  composite key, a renamed camera, or a deleted one can only ever cost a
  remembered convenience — never produce a binding the record cannot back.
- An emptied entry is deleted rather than stored as `{}`, so clearing every pick
  leaves the store the size it was before the panel was ever opened.

## 2 · Checkpoint-derived defaults

`PolicyConfigSummary` gained `n_action_steps` and `chunk_size` (both
`number | null`); `mockHub`'s fixture supplies them too (ACT 100/100, the flow
families 50/50).

### Engine precedence: `supports_rtc` → family list

`policySupportsRtc` now takes the **policy config object**, not a type string, so
the default engine, the `remoteEngineSupported` launch guard and the
"can't be in-painted" copy all read the same answer:

1. `supports_rtc === true | false` from the server **wins**, whatever the type is
   called. This is what makes `molmoact2` default to `rtc` at all — it is not,
   and will never reliably be, in the frontend's list.
2. `supports_rtc === null` (a server too old to send it, or a policy type newer
   than its table) falls back to `FLOW_POLICY_TYPES`.
3. Unknown on both sides reads as **no**: guessing `rtc` pairs the arm with a GPU
   server the operator was never told to start.

The two lists genuinely disagree — the frontend's carries `diffusion` (the fork's
classes say it cannot be in-painted), the backend's carries
`evo1`/`groot`/`molmoact2` — and with `supports_rtc` primary that disagreement
stops mattering for any current server. `defaultEngineForPolicyType` was renamed
`defaultEngineForPolicy` to match its new input.

### Horizon precedence: `n_action_steps` as a CEILING → `DEFAULT_HORIZON[engine]`

`horizonForEngine(engine, nActionSteps)`:

```
ceiling = n_action_steps when positive, else none
seed    = ceiling ? min(DEFAULT_HORIZON[engine], ceiling) : DEFAULT_HORIZON[engine]
```

**The clamp is a deliberate reading of "ceiling", and it is the one place this
slice interpreted the brief rather than following it literally.** The brief says
"seed the horizon from `n_action_steps` when present"; taken literally that
raises an ACT run's horizon from 16 to whatever the config declares (100 is the
lerobot default) and a flow run's from 50 to the same — a real behaviour change
for every existing remote run, in the direction of longer open-loop stretches
nobody asked for. Clamping instead:

- gives the motivating case the number it needs (MolmoAct2 `rtc`: `min(50, 30)`
  = **30**);
- leaves every existing default exactly where it was (ACT `sync`:
  `min(16, 100)` = 16; SmolVLA `rtc`: `min(50, 50)` = 50);
- and matches what `n_action_steps` actually IS — the count
  `predict_action_chunk` returns, i.e. the most a horizon may be, not the value
  it should take.

**If the coordinator wants the literal reading, it is a one-line change** in
`horizonForEngine` (drop the `Math.min`, return the ceiling when present).

Two places consume it, and both had to:

- the seeding effect in `DeployPanel` (extended, not duplicated). Its
  `seededEngineFor` ref now holds `policy_type|supports_rtc|n_action_steps`
  rather than the bare type, because two checkpoints of the same family can
  declare different chunk widths and keying on the type alone would leave the
  first one's horizon standing over the second. Still never re-seeds while a
  remote run is live.
- the engine switch in `RemoteRunFields` (the S3.5 "unless the operator typed
  their own" rule). Both sides of that comparison go through `horizonForEngine`
  now: without it, a 30-step checkpoint seeded to 16 for `sync` would read as
  "the untouched sync default" and be re-seeded to the rtc default of 50 —
  straight past the ceiling, into a silently dropped run.

The Horizon group says so in one sentence (en + zh-CN), and says something
sharper in `text-warn` when the typed horizon is **above** the ceiling — the
state that ends in a connected session receiving nothing.

## 3 · Task requirement — checked, generic, unchanged

`policyConfig.requires_task` is the only signal the frontend uses. It reaches
`deployGuards` as `requiresTask: !!policyConfig?.requires_task` and drives the
task field's helper text; `InferenceModal` (the legacy surface) reads the same
field. **Nothing frontend-side hardcodes a policy-family list for it**, so
molmoact2 joining `LANGUAGE_CONDITIONED_POLICY_TYPES` server-side is picked up
with no change here. Nothing was fixed because nothing was broken.

(The one family list touching `requires_task` in the frontend is
`lib/mockHub.ts`'s dev-mode FIXTURE — `policy === "smolvla" || policy === "pi05"`
— which is invented data for the mock server, not a guard. Left alone.)

## Deliberately not built

- **No dtype control.** `--model-dtype` stays out of the form and out of the
  generated `modal run` line: the decision is "measure first", and the flag is
  already available by hand (README, MolmoAct2 section).
- **No picker for LOCAL runs.** The component is written so the local path could
  adopt it, but only the remote path is wired. The local start payload, its
  guards and its binding derivation are byte-identical to before.
- **No guard-semantics change.** `deployGuards.ts` is untouched.
- **No RunVerbs / layout work.** S3.9 owns that; the DeployPanel diff is confined
  to the binding derivation, the remote start payload, the seeding effect and the
  camera alert.
- **No `frontend/dist`, `package.json` or `package-lock.json` change.**

## Bench recipe — MolmoAct2 from the panel

Prerequisites: a single-arm SO-101 record with **two** cameras configured and
plugged in (any names — `front` / `wrist` is fine, they will be bound as roles),
`makermodslab --sfu` running, and `modal` signed in.

1. Deploy panel → import / select `lerobot/MolmoAct2-SO100_101-LeRobot`, pick its
   checkpoint. The policy config loads: `supports_rtc: true`,
   `requires_task: true`, `n_action_steps: 30`, cameras `cam0` / `cam1` at
   224×224.
2. Arm the **remote** verb. Expect, with no further input:
   - engine preselected **Real-time chunking** (`supports_rtc: true`, not the
     family list — `molmoact2` is not in it);
   - horizon **30**, not 50, with the line "This checkpoint returns 30 steps per
     chunk…" under the transport group;
   - `s_min` visible (rtc only) at 4.
3. **Camera roles** appears under the run fields with two selects, labelled
   `cam0` and `cam1` (monospace, verbatim — they are the checkpoint's own keys).
   Bind each to one of the robot's cameras. The unmatched alert empties as you
   go, and the wording while it is non-empty points at the picker, not at Robot
   settings.
4. Type a task — it is **required** (`requires_task`), and blank is the failure
   MolmoAct2 does not report: the VLM is prompted with the literal
   `"The task is to ."`. Phrase it as an infinitive completion,
   e.g. `pick up the block and put it in the box`.
5. Launch the GPU (`GpuLaunchSection`), wait for the operator to appear in the
   room — cold start pulls **21.8 GB**, so budget several minutes — then press
   the remote verb.
6. Re-open the panel on the same checkpoint and robot: the two role picks come
   back. Unplug one of the bound cameras and Start blocks again (a pick of an
   unplugged camera is not a binding). Delete that camera in Robot settings and
   the pick is dropped silently, back to an empty select.

Cross-check against the generated `modal run` line (under "Run it yourself
instead"): `--horizon 30`, `--fps 30`, `--s-min 4`, `--video-codec H264`, and the
same `--task`. A horizon disagreement between the two sides is the failure that
reports nothing at all.
