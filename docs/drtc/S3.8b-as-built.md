# S3.8b — choosing which Modal workspace a launch bills

S3.8 gave the Lab a Start GPU button. It launched against whatever profile
happened to be active in `~/.modal.toml`, which on a machine with seven
profiles is a coin flip decided by whatever the operator last typed in some
other terminal. S3.8b lets the launch name its **profile** and **environment**,
per launch, without changing that machine-wide active profile.

## The two selection mechanisms, and why each is the one it is

Modal exposes exactly two per-invocation levers, and the launcher uses both:

| What        | How                                     | Where in the code           |
| ----------- | --------------------------------------- | --------------------------- |
| Profile     | `MODAL_PROFILE=<name>` in the child env | `modal_launcher.child_env`  |
| Environment | `modal run --env <name>`                | `modal_launcher.build_argv` |

**The profile is an environment variable, never `modal profile activate`.**
`activate` rewrites `~/.modal.toml`, which every terminal on this machine
shares. A web request that silently re-points the user's other shells is a side
effect a GET-or-POST has no business having, and it would outlive the launch.
`MODAL_PROFILE` is process-scoped, so one launch bills one workspace and
nothing else on the machine notices. It rides the child env next to
`LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET`, which travel there for the unrelated
reason that argv is world-readable in `ps`.

**The environment is a `modal run` option, so it goes BEFORE the wrapper path.**
`modal run [OPTIONS] FUNC_REF` — put `--env` after the path and Click hands it
to the wrapper's own `local_entrypoint`, which has no such parameter, and the
run dies on an unknown flag rather than billing the named environment. In
`build_argv` the flag is spliced immediately after `run`:

```
modal run --env staging /…/drtc/modal_policy.py --policy-path … --livekit-room …
```

**Empty means "the CLI decides", byte for byte the S3.8 behaviour.** Neither
value is emitted when blank (`--env ""` would name an environment called `""`,
and setting `MODAL_PROFILE=` would name a profile called `""`), so an API client
that never sends them sees no change at all: `MODAL_ENVIRONMENT`, then the
active local profile, then the workspace default, exactly as `modal run --help`
documents.

## The validation rule

`GET /api/v1/remote-inference/gpu/targets` lists what this machine can bill —
`modal profile list --json` for the profiles, and `modal environment list --json`
under `MODAL_PROFILE=<profile>` for that profile's environments (the CLI only
ever describes one profile's workspace, which is why the route takes an optional
`profile` query and echoes back which profile the environments belong to).

`modal_launcher.check_target` runs before anything is spawned:

- **Both empty → no check at all.** The default path pays for no listing and
  cannot fail because of one.
- **Either named → the listings are the authority.** An unknown profile or an
  unknown environment is a coded `400` refusal.
- **A listing that did not answer is also a refusal**, not a shrug. The
  asymmetry is about money: a typo is loud ninety seconds later in a log nobody
  is reading yet, but a real workspace belonging to someone else is silent and
  billed. Refusing costs a retry; guessing costs an A100-hour on the wrong
  account.

The listing ROUTE, by contrast, never 500s and never blocks a launch. A missing
`modal`, an expired token, a slow API and output this build cannot parse all
come back as `{code, message}` in the body (`gpu.cli_missing`,
`gpu.unauthenticated`, `gpu.targets_unavailable`). The panel then shows that
message verbatim in place of the two pickers and leaves **Start GPU live** — a
failed listing is not a failed launch, because with no selection the CLI still
resolves the target itself.

## What is echoed

`GpuStatusResponse` gained `profile` and `environment`, as launched, `null` when
the CLI chose (a different fact from an empty selection). The panel's ready line
turns that into "GPU running — this is billing. Billing to `work` · `makermods`.
Environment `main`." — the workspace is looked up in the listing, since the
status carries the profile name only. That line is the point of the feature: a
running A100 should say out loud whose account it is on.

The hand-typed fallback in `ModalRunLine` carries the same two values in the
same two forms (`MODAL_PROFILE=<name> modal run --env <name> …`), because it is
the ground truth an operator compares against when the fingerprint watchdog
fires — a line that billed a different workspace than the button would defeat
the comparison.

## The secret boundary

`~/.modal.toml` holds `token_id` **and** `token_secret` for every profile. It is
never opened — not to enumerate profiles, not to validate one, not to report
which is active. The two `--json` listing subcommands are the launcher's entire
view of Modal's local state, and they carry names and workspaces only. Nothing
on this path mutates: no `profile activate`, no `environment create`, no
`token`, no `run`. Both listings are bounded (`_TARGETS_TIMEOUT_S`, 8 s) and a
failed one is quoted back as one capped line of the CLI's own output.

## Bench checklist

1. Open the remote-inference form on a real robot; the **Modal profile** picker
   lists all seven profiles as `name · workspace`, defaulting to the active one.
2. Switch profile → the **Environment** picker re-lists (it should change, or at
   least re-fetch, for a profile in a different workspace).
3. Reload the page → both selections come back; `modal profile list` in a
   terminal still shows the ORIGINAL active profile, unchanged.
4. Start GPU with a non-default profile → the ready line names that profile and
   workspace, and `modal app list` under that profile shows the run.
5. Expand "Run it yourself instead" → the pasted line starts with
   `MODAL_PROFILE=<name> modal run --env <name> …` and runs as-is.
6. `mv ~/.local/bin/modal` aside (or unset the token) and reload → the pickers
   are replaced by the backend's message and **Start GPU is still clickable**.
