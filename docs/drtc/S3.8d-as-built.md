# S3.8d — shutdown stops the remote-inference session too

S3.8c taught the shutdown handler to stop the **GPU**. It still did not stop the
**arm**. `remote_inference` was the one robot-driving flow missing from
`shutdown_event`'s gather: teleoperation, recording, both auto-calibration
managers, local inference and replay were all stopped and waited for; the flow
whose child is *actually a separate process holding an energized follower* was
not.

So a uvicorn `--reload` restart (any save under `makermodslab/`), a Ctrl-C on
the dev launcher, or a `makermodslab --stop` during a live remote run left the
child to work out on its own that its supervisor had died — against this repo's
contract that **stopped means de-energized, and every flow returns the arm
before releasing torque**.

## What the child did when its parent died — as found

Three separate mechanisms, and only the third did anything.

**1. Signals do not reach it.** `remote_inference._spawn` passes
`start_new_session=True` (so a teardown can reap the whole tree). The child
therefore leads its own process group and session: a SIGTERM or SIGINT
delivered to the uvicorn worker reaches the worker alone.

**2. stdin EOF is ignored, deliberately.**
`drtc_protocol.pump_commands` — the daemon thread `LoopControl.start_command_pump`
runs — is a bare `for raw in stream:` loop. On EOF it falls through and the
thread simply ends. Its docstring is explicit about this:

> It does NOT stop the loop on EOF: an abandoned session is the server-side
> lease watchdog's job, and a child that killed itself on a closed pipe would
> drop an energized arm the moment a log pump hiccuped.

That reasoning holds for the *lease* case (the browser went away, the server is
still here). It does not hold when the **server** is what died: the lease
watchdog died with it. **This slice does not change that semantics** — see
"Not changed" below.

**3. What actually saved it: a broken stdout.** The parent's death closes the
read end of the child's stdout pipe. The control loop emits a `STATS` line once
a second through `_session_glue.emit` → `print(..., flush=True)`, which then
raises `BrokenPipeError` (Python sets `SIGPIPE` to `SIG_IGN`, so the write
returns `EPIPE` rather than killing the process). That unwinds
`robot_sync.run` / `robot_rtc.run`'s `except Exception` → `finally:` — the
teardown — within about a second.

**…except the teardown then broke on the same pipe.** The `finally:` opened
with three *unshielded* writes to that dead stdout:

```python
if start_poses and not control.quit_event.is_set():
    emit(EVENT_RETURNING)                       # <- raises BrokenPipeError
    print("[robot] returning to the start pose ...")
    shielded("the return to the start pose", return_step(...))
print("[robot] disconnecting...")
...
shielded("the torque release (robot.disconnect)", robot.disconnect, reraise=True)
```

`emit(EVENT_RETURNING)` raised straight out of the `finally:` block, skipping
the return-to-rest **and** `robot.disconnect()` — the call that releases torque.
The arm was left energized holding the policy's last command, in exactly the
case (nobody is left watching) where that is worst.

`tests/test_drtc_robot_sync.py::test_every_teardown_step_goes_through_the_shield`
did not catch it because it polices the steps that touch the *arm* and the
*transport* (`disconnect`, `close`, `return_to_start_poses`); the block's own
narration was not on the list.

### The child-side fix

In `makermodslab/drtc/_session_glue.py`:

- **`say(message)`** — a `print` that swallows `OSError`/`ValueError`. The
  teardown narrates through it, and so do `shielded`'s and
  `_shielded_disconnect`'s own diagnostics (a `print` inside the failure
  handler would have raised out of the shield itself).
- **`emit` still raises**, on purpose and now documented as such: it is the
  child's *only* parent-death detector, given (1) and (2) above. Swallowing it
  would have left the child running its full `duration_s` with nobody attached.

In both entrypoints' `finally:` (duplicated deliberately — S3.5's rule, pinned
by `test_both_engines_tear_down_the_same_way`):

```python
shielded("the RETURNING event", emit, EVENT_RETURNING, attempts=1)
say("[robot] returning to the start pose ...")
```

`shielded` already catches `Exception`, so the RETURNING event now behaves
exactly like the BYE event at the other end of the block. The step-label
sequence both entrypoints are asserted to share gains one entry at the front:

```
the RETURNING event → the return to the start pose → closing the transport
→ the torque release (robot.disconnect) → the BYE event
```

Net effect: **a parent that dies without saying anything at all** — SIGKILL, an
OOM, a power-cut on the laptop's Python process — now costs the arm about one
second of holding, then a full return-to-rest and torque release. That is the
backstop. The rest of this slice is the front door.

## The shutdown stop

`remote_inference.stop_for_shutdown() -> bool`, modelled on
`modal_launcher.stop_for_shutdown` and reusing the existing stop machine rather
than paralleling it. `handle_stop_remote_inference`'s tail was factored into
three named pieces both callers share:

| helper                       | what it does                                                              |
| ---------------------------- | ------------------------------------------------------------------------- |
| `_stop_child_and_wait(proc)` | `STOP` on stdin → wait → escalate → finalise                              |
| `_await_child_exit(proc)`    | `proc.wait(_STOP_WAIT_S)`, then `_terminate_tree` on timeout              |
| `_finalise_if_ours(proc)`    | terminal payload + `session_changed` release, unless the pump already did |

`stop_for_shutdown` then:

1. **Nothing running** → returns `False`, costs nothing. "Idle" is the normal
   case on the way out, not an exceptional one.
2. **A stop already in flight** (`phase == stopping`, from a Stop press or a
   watchdog) → `_await_child_exit` **without** writing another `STOP`. A second
   STOP is the *abort* gesture (cut the return short); on the way out we can
   still afford to wait, so we wait.
3. **Otherwise** → `handle_stop_remote_inference()`, which is the Stop control's
   own path: STOP → the child returns the arm → torque released → BYE → exit.
   It also covers the pre-spawn window (no child yet: set the cancel event and
   go idle).
4. **Then joins `_startup_thread`** if it is still alive — that is the preflight
   inside `_prepare_robot`, which has the follower's serial port open and cannot
   be interrupted mid-call. Leaving while it holds the bus is how the next boot
   finds it busy.

It never raises (the whole body is guarded) and emits the session_events
release exactly as a normal stop does, so the `SessionTracker` and the lease see
a clean end: `(remote_inference, True, stopping)` … `(remote_inference, False,
stopped)`.

### Bounds

| bound                          | value  | where it comes from                        |
| ------------------------------ | ------ | ------------------------------------------ |
| `rest_pose.RETURN_CEILING_S`   | 10.0 s | the return-to-rest's own hard ceiling      |
| `_STOP_WAIT_S`                 | 15.0 s | `RETURN_CEILING_S + 5` (disconnect + exit) |
| `_STARTUP_STOP_JOIN_TIMEOUT_S` | 5.0 s  | the preflight join                         |

No new constant was introduced: a shutdown-specific bound shorter than
`_STOP_WAIT_S` would cut a real return-to-rest short, and one longer would not
buy anything the escalation does not already cover. Typical cost is the two to
four seconds a real return takes; worst case is 15 s plus the `_terminate_tree`
escalation behind it.

## Hook ordering

In `server.py::shutdown_event`, `stop_for_shutdown` joins the **existing
`asyncio.gather` of hardware stops** — it does not run before it.

- **After the GPU stop**, which is already `await`ed to completion above, so the
  two never overlap. The existing comment there already anticipated this
  ("it is being stopped moments later anyway, by the same handler, with its own
  return-to-rest"). The order is the right one: a child that loses its policy
  for a second is a robot side that stops receiving actions and holds — exactly
  the state a return-to-rest wants to start from — whereas stopping the arm
  first would leave a GPU billing while we waited out its return.
- **Inside the gather** rather than sequenced before it, for the same reason the
  other six are: they are mutually exclusive in normal operation, so at most one
  has real work, and concurrency is free insurance if that invariant is ever
  violated.
- The parent-side empty-room watchdogs (`_ACTIVE_TIMEOUT_S`,
  `_CHUNK_TIMEOUT_S`) are armed only in `warming_up`/`easing`, and if one does
  fire between the GPU stop and ours, `stop_for_shutdown`'s in-flight branch
  waits its return out instead of aborting it.

## Launcher grace — the arithmetic does NOT fit, and is left alone

`makermodslab/scripts/makermodslab.py::_terminate_tree` signals the leader alone
and waits `_LEADER_GRACE_S = 10.0` before walking the tree with SIGTERM →
SIGKILL. That governs the dev launcher's Ctrl-C and `makermodslab --stop` (not
`--reload`, where uvicorn's own reloader terminates and joins the worker with no
deadline of its own).

The DRTC child **is** in that walk: `parent.children(recursive=True)` follows
real parent links, and `start_new_session=True` escapes the process *group*, not
the parent-child relation. So a grace that expires mid-return SIGTERMs the child,
whose default SIGTERM disposition kills it without running the `finally:`.

The budget after this slice:

```
GPU stop            ~2 s typical, bounded 5 s   (S3.8c)
remote-inference    ~2-4 s typical, bounded 15 s (+ terminate escalation)
uvicorn graceful     ~1 s
                    ------------------------------------
typical             ~5-7 s      worst  ~21 s+
_LEADER_GRACE_S     10.0 s
```

The typical case fits; the worst case does not. **The constant was not
changed** — that is a coordinator decision, not this slice's. Two options:

- **A (recommended): `_LEADER_GRACE_S = 22.0`** = 5 (GPU bound) + 15
  (`_STOP_WAIT_S`) + 2 (uvicorn). The wait returns as soon as the tree is gone,
  so it costs nothing in the common case; the only price is that a genuinely
  wedged backend takes 22 s instead of 10 s to be force-killed on Ctrl-C.
- **B: leave it at 10.0.** A slow return-to-rest gets cut short on the launcher
  paths.

Either way this is **not a regression**: today the grace expires with the child
never having been told to stop at all, so it is SIGTERMed mid-policy with the
arm energized. B is strictly better than that; A closes the gap.

## Not changed

- **stdin EOF still does not stop the child.** Making EOF mean STOP would change
  `drtc_protocol`'s documented command semantics, and the broken-stdout path
  above already gives the same outcome (return-to-rest + torque release) about a
  second later, without touching the protocol. Flagged for the coordinator
  rather than decided here.
- The Modal launcher, the SFU, the frontend, every other flow's stop.

## Bench checklist

1. Start a remote-inference run and let it reach `running` (chunks arriving).
2. Touch any file under `makermodslab/` to force a `--reload` restart.
3. Expect: the arm eases back to its start pose and goes limp **before** the
   worker comes back up — not a snap, not a drop, not a still-energized arm.
4. `~/.cache/huggingface/lerobot/logs/drtc/sessions/<ts>.log` ends with
   `RETURNING` → `[robot] disconnecting...` → `BYE`, and the new server's
   `GET /api/v1/remote-inference-status` reads `exited: true, phase: stopped`.
