# S3.8c — stopping the GPU actually stops the GPU

S3.8 shipped on an assumption that turns out to be false: that killing the
local `modal run` client stops the Modal app under it. It does not. On
2026-09-03 the Lab left an A100 running three times, each time for the 5-7
minutes Modal's own client-heartbeat timeout took to notice nobody was
attached. This slice makes every stop path stop the app, records the app id so
a process that has lost its client can still stop one, and reaps an orphan left
by a Lab that died badly.

## The leak, and why it was invisible

In the installed client (`modal/runner.py::_run_app`) the app-stop RPC —
`AppClientDisconnect`, which terminates an ephemeral app's tasks — is sent
from exactly three places: the entrypoint completing, `except BaseException`,
and `except KeyboardInterrupt`. **There is no SIGTERM handler.** So:

| How the client died                                   | App stopped? |
| ----------------------------------------------------- | ------------ |
| Ran to completion                                     | yes          |
| Raised (bad room, a container traceback)              | yes          |
| SIGINT — a terminal's Ctrl-C                          | yes          |
| SIGTERM / SIGKILL — every stop path the Lab had       | **no**       |

Every Lab stop path went through `rollout._terminate_tree`, which is
SIGTERM→SIGKILL over the process group. The three leaking paths:

- `POST /remote-inference/gpu/stop` — the panel's **Cancel** (while `starting`)
  and **Stop** (while `ready`), plus the cold-start overrun and the idle
  auto-stop, which are implemented by the same kill.
- the app's `shutdown_event` — which did not stop the GPU at all, so a uvicorn
  `--reload` restart (any save under `makermodslab/`) orphaned the client.
- the dev launcher's Ctrl-C, whose `_terminate_tree(pid)` walks the whole
  psutil tree and SIGTERMs the `modal run` client as a grandchild — before the
  backend's own shutdown handler could have reached it. `makermodslab --stop`
  did the same.

It was invisible from inside the Lab because the LOCAL side worked perfectly:
the client died, the pump saw EOF, the panel went from `stopping` to `idle` in
under a second. Nothing in the Lab observes the app.

Ground truth for any of this, then and now:

```
MODAL_PROFILE=makermods modal app list       # State: ephemeral = still running
```

## What now happens on a stop

```
SIGINT to the client's process group          _graceful_terminate
   └─ exits within _SIGINT_GRACE_S (5s)? ──> clean: the client sent the RPC
   └─ still there? ──> rollout._terminate_tree (SIGTERM → SIGKILL, unchanged)
                       ──> not clean
arm the drain deadline (_STOP_DRAIN_TIMEOUT_S, unchanged)
not clean ──> modal app stop --yes <app id>   _settle_app / stop_app
```

- **SIGINT goes to the GROUP**, because that is what a terminal delivers on
  Ctrl-C — the exact signal path Modal's client is written against.
- **`_SIGINT_GRACE_S = 5.0`.** The client sends `AppClientDisconnect`
  immediately and prints "Stopping app"; observed exit is ~2 s. It then waits
  on the final log stream, which Modal bounds itself (`logs_timeout`, 10 s by
  default) — so this constant has to cover the RPC, not the log drain.
  Escalating past it is not lossy: `_settle_app` then stops the app over the
  API anyway.
- **`rollout._terminate_tree` is untouched.** Other runners depend on its
  behaviour and none of them has an app on a remote machine; the graceful step
  is layered in front of it, launcher-local.
- **`_APP_STOP_TIMEOUT_S = 15.0`** bounds `modal app stop`. `--yes` is not
  optional — without it the CLI prompts and a server has no terminal, so it
  aborts with "no interactive terminal detected". The profile rides
  `MODAL_PROFILE`, as a launch and a listing already do: an app id belongs to
  ONE workspace. "App is already stopped." is success.
- The app stop runs AFTER the drain deadline is armed, so it never lengthens
  the window in which the launcher reports `stopping`.

## The app id, recorded

The client prints its app page as one of its first lines — and Rich WRAPS it,
so the sentence and the url are on different lines:

```
✓ Initialized. View run at
https://modal.com/apps/makermods/main/ap-QfTK2AxcfbJnnY1kLS7Y22
```

`parse_app_id` therefore anchors on the url (`modal.com/apps/…/ap-…`), never on
"View run at". That is also the stricter anchor: an `ap-`-shaped token in a
traceback can never be mistaken for an app id.

The pump captures it (beside `parse_phase`), the status echoes it as `app_id`,
and `{app_id, profile, started_at}` is written to
`~/.cache/huggingface/lerobot/drtc_gpu_app.json`
(`utils.config.DRTC_GPU_APP_FILE`, atomic write). It is cleared only by the app
it names, so a stop settling late cannot delete the id of a run that started
after it. Who clears it:

- a stop (`_settle_app`) — when the client exited on the SIGINT, or when the
  API stop succeeded. A FAILED API stop keeps it, so the next boot tries again.
- a client that ended by itself with `rc >= 0` (`_handle_exit`) — completion or
  an uncaught exception, both of which run modal's own disconnect. Without this
  every clean run would leave a stale record and the next boot would announce
  an orphan it never had.
- nobody, when `rc < 0` — a signal death this launcher did not ask for
  (someone's `kill -9`) sends no disconnect, so that record is exactly what the
  next boot needs.

## The orphan reaper

On the **server's startup event** (`makermodslab.server.startup_event` →
`modal_launcher.reap_orphan_app_async`), on a daemon thread: if the record
names an app and nothing is running in this process, `modal app stop --yes` it
and put a line in the idle status's `message` —

> Stopped an orphaned GPU app ap-… from 2026-09-03 18:49 — it outlived the Lab
> that started it.

or, when it fails, the app id, the CLI's own reason, and the command to run by
hand. It is bounded, best-effort, and never blocks or refuses a launch.

Startup rather than the first `GET /gpu` (both were on the table): a GET must
not carry a Modal API call, and startup is early enough that the message is
already in the very first status the panel reads. Startup rather than module
import: an import-time subprocess would fire in tests, in SDK clients, and in
`makermodslab --stop`.

## Shutdown ordering

Two changes, and together they mean the client always gets its SIGINT from the
process that spawned it:

1. **`server.shutdown_event` stops the GPU first**, right after
   `job_registry.shutdown()` and before the arm stops — synchronously (in a
   thread), via `modal_launcher.stop_for_shutdown()`. A fire-and-forget stop on
   the way out is not a stop: it would outlive the process it runs in. It costs
   ~2 s when a GPU is up and returns immediately when none is. Ahead of the arm
   stops on purpose: a remote run whose policy vanishes for that moment is a
   robot side that stops receiving actions and holds, and it is being stopped
   by the same handler moments later with its own return-to-rest.
2. **The dev launcher signals the LEADER first** (`scripts/makermodslab.py`,
   `_terminate_tree(pid, …, grace=_LEADER_GRACE_S)`): terminate the leader
   alone, wait up to 10 s for the tree to go quiet by itself, and only then
   walk the snapshot as before (terminate → wait → kill). That is what gives
   the uvicorn supervisor time to shut its worker down and the worker time to
   run the handler above. It costs nothing in the common case — the wait
   returns as soon as the tree is gone — and it did NOT need the launcher to
   know anything about the modal child. `npm run dev` is the one exception
   (`grace=0.0`): it routinely leaves vite behind rather than taking it down,
   so waiting on that tree would add ten seconds to every Ctrl-C and change
   nothing. `makermodslab --stop` uses the same grace, so it behaves like a
   Ctrl-C.

## The Cancel button

Reported as "the cancel gpu button is not working". Traced end to end —
`GpuLaunchSection` (the button is `disabled={busy}`, i.e. only while a request
is in flight or the state is already `stopping`) → `useGpuLauncher.stop` →
`POST /gpu/stop` → `modal_launcher.stop()` → `stopping` → the terminate thread
→ the pump's EOF → `idle`. **The local half was never broken.** The bench logs
show it working: `logs/drtc/gpu/1788488005.log` ends mid-`Fetching 18 files`,
i.e. the client was killed exactly where Cancel killed it.

What was broken is what Cancel is FOR. The container it was meant to cancel
kept running: still billing, and still sitting in the LiveKit room as the
`policy` participant — so a start right after a cancel joined a room that
already had a policy in it. That is the leak above, and items 1-3 fix it.

Two things found while tracing that are NOT fixed here, both reported rather
than changed:

- A Cancel that races a transition to `failed` (a cold-start overrun, or the
  client exiting on its own within the panel's 2 s poll gap) gets a 409
  `gpu.not_running` and the red line under the panel, because `stop()` refuses
  in `failed`. Correct as a contract, momentarily confusing as a UI.
- While `stopping`, the button's label flips from Cancel to Stop and goes
  disabled with a spinner. Worst case that lasts ~25 s (SIGINT grace +
  escalation + drain bound); typically under a second.

## Status echoes the transport tuple

`app_id`, `task`, `horizon`, `fps`, `video_codec` and `s_min` join the status
dict and `GpuStatusResponse` (null when idle). The panel's drift warning now
compares the form against the SERVER's record and falls back to the tab's
`launched` memory only when the echo is incomplete — so it fires after a page
reload and for a GPU another tab started, neither of which the tab's own memory
could cover. `s_min` is echoed for both engines but compared only for `rtc`,
because that is the only engine whose wire carries it. The block's copy and its
restart button are unchanged.

## Bench checklist

1. `makermodslab --dev --sfu` (or `--sfu-external-ip`), open Deploy, **Start
   GPU**; when the panel names an app id, `MODAL_PROFILE=makermods modal app list`
   → State `ephemeral`.
2. **Cancel** while `starting` → panel goes idle, and `modal app list` shows
   that app `stopped` within seconds (not 5-7 minutes).
3. Let one reach `ready`, press **Stop** → same check, same answer.
4. With a GPU `ready`, save a file under `makermodslab/` to force a `--reload`
   → the server log says "Stopped the GPU policy server on shutdown", and
   `modal app list` says `stopped`.
5. With a GPU `ready`, Ctrl-C the dev launcher (and separately,
   `makermodslab --stop`) → same two checks.
6. With a GPU `ready`, `kill -9` the uvicorn worker, then restart the Lab →
   the idle panel says "Stopped an orphaned GPU app ap-… from …", and
   `modal app list` agrees. `~/.cache/huggingface/lerobot/drtc_gpu_app.json` is
   gone afterwards.
