## 1. Process model

### 1a. Where the launcher lives

**Options.** (A) inside `remote_inference.py`; (B) `makermodslab/drtc/modal_launcher.py`; (C) `makermodslab/modal_launcher.py` (top level).

**REC: (C), `makermodslab/modal_launcher.py`.**

- (A) is wrong on size and on ownership: `remote_inference.py` is already 1724 lines and its module docstring is an essay about owning *only* the robot side. A Lab-level resource with its own lifetime does not belong in a module whose globals are all `_go_idle_locked()`-reset per session.
- (B) is wrong on the invariant CLAUDE.md states and `drtc/__init__.py` restates verbatim: *"This package is only importable with the optional `drtc` extra installed … nothing in the Lab imports it at startup. The one exception is `_env`."* The launcher only shells out to a binary — it imports no LiveKit, needs no extra, and must be importable at server boot for its routes. Putting it in `drtc/` would either break that sentence or require a second documented exception.
- (C) is the honest home: sibling of `remote_inference.py`, imports nothing from `drtc/`, and refers to the wrappers **by path** (`Path(__file__).parent / "drtc" / "modal_policy.py"`) so it never imports `drtc/__init__` either.

Log file: `Path(DRTC_LOG_DIR) / "gpu" / f"{int(time.time())}.log"` — a **sibling** of `sessions/`, by the same argument the existing `_LOG_DIR` comment makes ("in their own subdirectory so a session log can never be mistaken for one of those").

### 1b. Binary discovery

Mirror **`sfu.find_livekit_server`, not `system._find_uv`** — same ladder, but `sfu.py` injects `which` as a parameter (`which: Callable[[str], str | None] = shutil.which`) which makes it unit-testable with a fake PATH; `_find_uv` is not injectable. Copying the testable shape costs nothing and S3.6 has just set it as the house pattern.

```
def find_modal(env=None, which=shutil.which, is_file=os.path.isfile) -> str | None
```

Ladder: `MAKERMODSLAB_MODAL_BIN` (must point at an existing file — a typo'd override **refuses**, never falls through to PATH; that rule is `sfu.find_livekit_server`'s and it exists so you can't silently run a different build than you asked for) → `shutil.which("modal")` → `~/.local/bin/modal` → `/opt/homebrew/bin/modal`, `/usr/local/bin/modal` → `None`.

None → refuse with `gpu.cli_missing` and the message naming `uv tool install modal` (the actual install route on this bench — the CLI is a uv tool, and `uv pip install modal` into the Lab venv would be the *wrong* fix since it would drag Modal's deps into the app's environment for no benefit).

### 1c. The secret in argv — the one wrapper change

**Today the secret would be in `ps`.** `modal run … --livekit-api-secret <secret>` is argv on the local machine. There is **no env-based alternative in the wrappers today**: `main()` takes the value only as a parameter and forwards it to `fn.remote(...)`; nothing in either wrapper reads `os.environ` locally.

**REC — smallest possible change, ~6 lines in each wrapper, identical in both:**

```python
# in main(), before choosing the twin:
livekit_api_key = livekit_api_key or os.environ.get("LIVEKIT_API_KEY", "")
livekit_api_secret = livekit_api_secret or os.environ.get("LIVEKIT_API_SECRET", "")
```

Why this works and is safe: `@app.local_entrypoint()` bodies execute **on the user's machine**, in the `modal` CLI's interpreter, with the launcher's inherited environment. The resolved value then travels as a `fn.remote(...)` kwarg over Modal's own TLS channel — never argv, never `ps`. The flag still wins when present, so every human invocation and every line in `docs/drtc/README.md` is unchanged.

**Scope the fallback to the two secrets only — deliberately NOT to `livekit_url` / `livekit_room`.** Those are not credentials; keeping them as flags means the launched line is self-documenting in `ps` and in the log, and — more importantly — it keeps "which SFU, which room" a decision that is *visible* rather than one that can be flipped by a stray `LIVEKIT_URL` in an operator's shell. That ambient-env hazard is real and is the one behaviour change here: an operator with `LIVEKIT_API_SECRET` exported who previously fell through to the `LiveKit-cloud` Modal secret will now send their local one. Restricting to credentials that are in practice the same credentials keeps the blast radius to "wrong password" rather than "wrong room, silently, forever" (which is precisely the failure class `--livekit-room` was added to close).

Alternative considered and rejected: namespacing the fallback (`MAKERMODSLAB_LIVEKIT_API_SECRET`). It removes the ambient hazard entirely but introduces a variable name that exists nowhere else in either project and that a human debugging by hand would never guess. Worth reconsidering if the coordinator weights the hazard higher than I do.

Cost: two files, kept byte-identical in the changed region — both wrappers carry the standing note *"these two wrappers are deliberate near-duplicates … Fix bugs in both."*

### 1d. Attached vs `--detach`

**REC: attached (no `-d`) in S3.8; no `detach` option field.**

- Attached makes the local `modal run` process the app's lifeline: killing the process group stops the app. That is exactly the cost-safety property we want, and it composes with `_terminate_tree`'s existing SIGTERM→SIGKILL-over-the-group discipline for free.
- Detached needs `modal app stop <app id>`, persisted app ids, reattachment on Lab restart, and it introduces the one genuinely expensive failure mode in this whole design (an orphan A100 nobody knows about). Not worth it to buy "the GPU survives a Lab restart" for a slice whose entire premise is that the GPU is started ~1 minute before a run and stopped after.
- The trade to state plainly: **attached means the GPU dies with the Lab.** That is acceptable because the robot session dies with it too (the child is a Lab subprocess), and the child's own `finally:` returns the arm to rest before releasing torque.

### 1e. The argv builder, and the structural hedge against S3.6

```
[modal_bin, "run", str(WRAPPERS[engine]),
 "--policy-path", policy_hub_id,
 *(["--task", task] if task else []),
 "--horizon", str(horizon),
 "--fps", str(fps),
 *(["--s-min", str(s_min)] if engine == "rtc" else []),
 "--video-codec", video_codec,
 "--livekit-room", room,
 *(["--tailscale", "--livekit-url", url] if plan.needs_tailscale else []),
 # key/secret NEVER here — they ride the child env (1c)
]
```

No shell. `subprocess.Popen(list, start_new_session=True, stdin=DEVNULL, stdout=PIPE, stderr=STDOUT, env={**os.environ, "PYTHONUNBUFFERED": "1", "LIVEKIT_API_KEY": …, "LIVEKIT_API_SECRET": …})`, and — deliberately unlike `remote_inference._spawn` — **`stdin=DEVNULL`**: there is no command protocol here, and leaving stdin open on a process the Lab may need to kill buys nothing.

**The hedge:** resolve `{url, room, api_key, api_secret, needs_tailscale}` in **one** function, `resolve_transport_plan()`, returning a frozen dataclass. Everything else — the argv builder, the child env, the frontend's generated line, the tests — consumes the plan. When S3.6 answers "does `--sfu-external-ip` remove the need for `--tailscale`?", that answer changes **one function body**, not four call sites. This is the single most valuable structural decision in the plan, because it is the only place S3.6 and S3.8 genuinely collide.

`--policy-path` is required by both entrypoints (no default), so a start with an empty `policy_hub_id` must be refused **before** spawning, with `gpu.launch_failed` and a message naming the field — otherwise the failure is a Click usage error 90 seconds into a log the user is watching for cold-start progress.

### 1f. Log parsing → phases

Reuse `drtc_protocol`'s stated rule verbatim: **match the prefix anywhere in the line**, because a log record flushed without its newline (and Modal's own line decoration) would otherwise swallow the event. Pure function:

| substring | phase |
|---|---|
| `[tailscale] relay` | `tailscale_up` |
| `[policy] loading '` | `loading` |
| `[policy] warming up model` | `warmup` |
| `[policy] connecting to` | `connecting` |
| `[policy] connected as` | **`connected`** ← readiness |
| `[policy] claimed control as` | `claimed` |

`connected` is the state that flips `gpu.state` to `ready`, **not** `claimed`: `policy_rtc.py:542` says the claim runs in the background and `:359`'s build marker names it "non-fatal", so a healthy run may never print `claimed`. Treat `claimed` as a display refinement only.

Also parse, best-effort: Modal's startup app URL line, for `app_id` / a dashboard link. **I could not verify its exact format without running `modal`** — treat it as a `re.search(r"modal\.com/apps/\S+")` that yields a display link, and get `app_id` from `modal app list --json` if it is ever actually needed (it isn't, for attached runs). Flag for bench confirmation.

### 1g. Modal auth

The CLI reads `~/.modal.toml` (or `MODAL_TOKEN_ID`/`MODAL_TOKEN_SECRET`). **The Lab never reads, parses, echoes or requires that file** — it inherits the environment and lets the CLI do its own thing. When it is missing, `modal run` exits nonzero within a second or two with an auth error naming `modal token new`. Detect it by (a) nonzero exit before any `[policy]` line and (b) `token`/`auth`/`not authenticated` in the captured output; map to `gpu.unauthenticated` with a message quoting the CLI's own line and naming `modal token new`. Do **not** pre-check by running `modal token info` — an extra subprocess per start, and the real invocation gives a better error anyway.

## 2. Session integration

### The two shapes

**(A) `launch_gpu: bool` on `RemoteInferenceOptions`, default false.**
**(B) a separate Lab-level resource: `POST /api/v1/remote-inference/gpu/start`, `POST …/gpu/stop`, `GET …/gpu`.**

**REC: (B), decisively.** Five independent arguments, all from existing code:

1. **The design rule forbids A's natural shape.** SLICE3 §2B: *"launch the GPU in a pre-claim phase, poll the room for the operator, and claim/connect the arm only once it is there."* Under (A), `handle_start_remote_inference` sets `remote_inference_active = True` at line 1275 — **before** the extra check, before credentials, before the probe. A 60–180 s pre-claim wait inside that function means the flag is set, and the arm is nominally held, for three minutes while nothing touches hardware. The alternative (claim later) would rewrite the claim-first race protection that comment exists to provide.
2. **The mutex would lie.** `remote_inference_active` is one of eight `robot.busy.*` discriminants, equality-asserted in `tests/test_api_errors.py::BUSY_DISCRIMINANTS`. Under (A) it would refuse teleop, record, replay and both calibrations for three minutes **while the arm is completely free**. That is a user-visible regression in exchange for nothing.
3. **Three safety-critical sets would have to widen.** `_WINDING_DOWN_PHASES = frozenset({"releasing", "stopping"})`, `_WATCHED_PHASES`, and `_dispatch_stop` all currently assume a session that has (or is about to have) a child holding the bus. A pre-claim phase with no child and no arm would need each one audited — SLICE3 §3 already spent a paragraph on exactly this hazard for the far smaller case of the return-to-rest window.
4. **The lease.** Mechanically a 3-minute wait is survivable (browser heartbeat ~20 s, `useSessionHeartbeat`), but it means an expiry tick can land in a window where `_dispatch_stop("remote_inference")` has nothing to stop but a cloud subprocess — i.e. the lease's safety-stop would be doing something that is not de-energizing an arm. The lease's whole promise is the opposite.
5. **CLAUDE.md's own framing settles it.** *"This process owns **only** the robot side."* A GPU launch is a Lab-level resource **exactly like a training job** — and the precedent is already in the tree: `jobs.training_is_active()` is consulted by the session but is not part of it; `InstallManager` in `utils/system.py` is a module-level singleton with `state: idle|installing|done|error`, a `Popen`, a log queue, a lock and two routes (`POST /system/training-extra/install`, `GET …/install-status`). **That is the shape to copy, almost line for line.**

And the clinching UX argument: **the readiness signal already exists and is already being polled.** `GET /api/v1/remote-inference/transport` reports `operator_present` from `_probe_room`, and `useRemoteInferenceTransport` polls it. "Start GPU" → progress → the existing transport poll flips `operator_present` to true → "Run it remotely" unblocks. (B) needs **zero** new session surface to deliver the entire briefed experience.

### Shape of (B)

Module singleton in `makermodslab/modal_launcher.py` — `_state_lock`, `_proc`, `_state`, `_started_at`, `_log_path`, `_message`, `_last_line`, `_phase`, `_app_url`, `_clock = time.monotonic` (injected, per house style).

Phases (the log-derived ones above) sit *inside* the coarse state:

```
gpu: {
  state: "idle"|"starting"|"ready"|"failed"|"stopping",
  phase: str|null,          # tailscale_up|loading|warmup|connecting|connected|claimed
  engine: "sync"|"rtc"|null,
  policy_hub_id: str|null,
  room: str|null,
  log_path: str|null,
  app_url: str|null,        # display only; null for now (1f)
  started_at: float|null,   # wall clock
  elapsed_s: float,
  message: str|null,        # terminal reason, or the last [policy] line while starting
  hint: str|null,
  idle_stop_in_s: float|null,
}
```

`app_id` from the brief becomes `app_url` (display-only) — with attached runs there is nothing to address by id, and shipping an `app_id` field implies a reattach contract S3.8 does not have. Add it when `--detach` lands.

**Readiness is not the launcher's to declare.** `state: "ready"` is a *hint* from the log parse; `handle_start_remote_inference`'s `_probe_room` rung stays the sole authority for "may I energize the arm". One source of truth, unchanged.

### Error codes

**REC: a new `gpu.*` domain** — `gpu.cli_missing`, `gpu.unauthenticated`, `gpu.already_running`, `gpu.not_running`, `gpu.launch_failed`.

The argument is the taxonomy's own, quoted from `api_errors.py:139` for `transport`: *"an external service this node depends on. Folding it into `hardware.connect_failed` would lie (that is the serial bus), and so would `system.*` (it is not this process)."* Modal is a second external service with a different remedy set. `transport.*` is rejected because the GPU is neither the SFU nor the room, and the four transport rungs' remedies are already carefully distinguished — a fifth meaning would blunt them. `system.*` is rejected because `gpu.unauthenticated` and `gpu.launch_failed` are facts about Modal, not about this machine (`gpu.cli_missing` alone would fit `system.*`, which is not enough to move the set).

**Caveat, and open question #1:** S3.6 is concurrently adding the `sfu` domain. Two new level-1 domains in one week is a taxonomy decision, and `DOMAINS` in `tests/test_api_errors.py:34` is one frozenset both branches edit — a guaranteed (trivial) textual conflict. Cost: +1 line in `DOMAINS`, grammar test passes automatically (`gpu.cli_missing` matches `^[a-z]+(_[a-z]+)*(\.[a-z]+(_[a-z]+)*){1,2}$`).

### Ratchet / OpenAPI cost

- `V1_ONLY_ROUTES` **+3** (it is the register that grows — allowed).
- `UNTYPED_V1_ROUTES` **unchanged** — all three ship typed, per "new routes ship typed".
- `LEGACY_ROUTES` **unchanged** — nothing goes on the flat mount.

## 3. Stop ordering and failure modes

### Ordering

**Robot session stop → child returns to rest → torque off → *then* GPU stop.** With shape (B) this is not enforced by a code path at all — the two resources are independent, so there is no way for the arm's release to end up behind a cloud API call. That is the property SLICE3 §2B demanded (*"never make the arm's release wait on a cloud API"*), and (B) gets it structurally rather than by discipline.

**`_dispatch_stop("remote_inference")` must NOT stop the GPU.** A lease expiry is a *safety* stop whose one job is de-energizing an arm; adding a second, slower, network-dependent action to that path is exactly wrong. The GPU is reclaimed by the idle auto-stop instead.

### Should the launcher's exit trigger a session stop?

**REC: no.** Three reasons:

1. **The watchdogs already do it, better.** `_watchdog_failure_locked` fires on no-ACTIVE-in-15 s and no-chunks-in-10 s, and each produces a *diagnosed* message naming the fingerprint or the three causes. They measure the room — the thing that actually matters — rather than a proxy for it.
2. **`modal run`'s local exit is a weak signal.** It can end on a log-stream disconnect while the app is fine; conversely it can linger. Wiring it to a hardware stop would add a way for the arm to stop that is not the user, not the lease and not the room.
3. **Direction of dependency.** (B)'s whole justification is that the session does not own the GPU. Letting the GPU stop the session re-couples them through the back door.

**What it *should* do:** on a nonzero exit while a remote session is live, log at WARNING, set `gpu.state = "failed"` with the classified message, and let the panel show both cards. The session's own watchdog message ("the policy is in the room but sent no chunks…" / "no policy joined room X…") and the GPU's failure line then sit side by side, which is strictly more diagnostic than a stop the user didn't ask for.

### Failure modes

| Mode | Detection | Response |
|---|---|---|
| **Modal cold-start overrun** | no `[policy] connected as` within `_COLD_START_TIMEOUT_S` | **REC 300 s.** 60–180 s is the realistic band, but a cold `hf-cache` volume plus a first-ever VLA `from_pretrained` can exceed 180 and a false failure at that moment is maximally annoying. `_terminate_tree` the group, `state="failed"`, message quoting the last parsed phase ("stuck at `loading`" is a very different diagnosis from "stuck at `tailscale_up`"). |
| **Tailscale auth-key expiry** | `_tailscale_up(timeout=90)` raises in-container; `[tailscale-relay] upstream dial failed:` or a tailscale error in the stream, then exit | Match `authkey`/`auth key`/`expired`/`tailscale up` in the captured output → specific message: *"the `tailscale-auth` Modal secret's TS_AUTHKEY has expired — mint a new **ephemeral** key and `modal secret create tailscale-auth TS_AUTHKEY=… --force`."* High value: this same failure currently reaches the operator as `transport.no_policy`, whose message already lists it as one of *three* possible causes. The launcher can now say **which one**. |
| **Modal auth missing** | fast nonzero exit, no `[policy]` line, auth text | `gpu.unauthenticated`, name `modal token new` (§1g) |
| **`modal` binary missing** | `find_modal()` → None | `gpu.cli_missing`, name `uv tool install modal`. Synchronous 400 before anything spawns. |
| **Bad `--policy-path`** | container raises inside `from_pretrained`; run ends, nothing joins the room | `state="failed"` with the container's traceback tail; and separately the session's `_ACTIVE_TIMEOUT_S` watchdog would catch it if a session were started anyway |
| **Fingerprint mismatch** | GPU healthy, robot healthy, zero chunks | Already owned by `_CHUNK_TIMEOUT_S`. The launcher adds nothing — but the panel can now show both sides' settings from one object, which is the real mitigation. |
| **Lab restart with a live GPU** | n/a for attached runs — the app dies with the process group | If `--detach` is ever added: persist `app_id`, reattach by **id only**. `modal app list --json` lists every running app *in the workspace*, including other people's; matching on the app name (`lerobot-drtc-policy` / `lerobot-drtc-full-policy`) could adopt or stop a stranger's run. Name-matching is a footgun, not a fallback. |

### Cost awareness

Back-of-envelope: `_FN_KWARGS["gpu"] = "A100"` at Modal is roughly **$2–4/hr**. `_FN_KWARGS["timeout"] = 2h` already caps a single forgotten run at **~$4–8**. The unbounded case only exists if `--detach` ships (an overnight orphan ≈ **$25–45**), which is one more reason S3.8 stays attached.

**REC: idle auto-stop at `_GPU_IDLE_STOP_S = 600.0` (10 minutes)** — measured from whichever is later: the GPU reaching `ready`, or the end of the last remote-inference session. Ten minutes is longer than a realistic gap between two runs (re-arm the form, reposition the block, re-grip) and costs at most ~$0.5 of waste. Implement as a check inside the existing status poll and the log pump — **not a new thread**; the same argument `_check_watchdogs`'s docstring makes ("Deliberately NOT a thread: there is nothing to watch that does not already wake one of those two"). Expose `idle_stop_in_s` so the panel can count down, and the panel should say plainly that a ready GPU is **billing**. Visibility is the cheapest cost control there is.

## 4. What this does NOT need

- **No `modal` Python dependency** anywhere — not in `[drtc]`, not in `[dev]`, not in the base. The CLI is discovered as a binary and shelled out to. (Adding it would also be wrong: the Lab venv's Python is not the uv-tool interpreter Modal expects.)
- **No `/reset` wiring**, ever. SLICE3 §2B: it re-spawns the *last* run globally from a `modal.Dict` with no session identity, so a Lab-driven reset could resurrect someone else's run. It stays a documented human escape hatch.

- **No new session kind, no options-model field, no `_dispatch_*` arm, no `robot.busy.*` discriminant, no `SESSION_KINDS` entry.**
- **No reading of `~/.modal.toml`.**
- **No changes to `_probe_room`, `_robot_sync_args`, the phase vocabulary, or either watchdog.**

## 6. Frontend

**New `GpuLaunchSection.tsx`**, placed between `RemoteRunFields` and `TransportSection` — `RemoteInferenceBlock.tsx`'s own docstring already declares the order as *"what to configure, what to launch on the GPU, what the transport looks like, and then what the run is doing"*, so this slots into a hole the file predicted.

**New `hooks/useGpuLauncher.ts`** — poll `GET /api/v1/remote-inference/gpu` at ~2 s while `starting`, ~10 s otherwise, 0 while `idle` after a settled failure.

**Button states**

| state | UI |
|---|---|
| `idle` | "Start GPU" (enabled once `policyHubId` resolves), subtext naming the engine's wrapper |
| `starting` | spinner, elapsed, the current phase as prose (*"loading the checkpoint…"*, *"warming up…"*, *"connecting to the room…"*), last log line in a mono strip, "Cancel" |
| `ready` | green, **"GPU running — this is billing"**, idle-stop countdown, "Stop GPU" |
| `failed` | `message` + `hint`, "Try again", link/path to the log |
| `stopping` | disabled spinner |

"Run it remotely" continues to unblock off the **existing** `useRemoteInferenceTransport` poll's `operator_present` — not off `gpu.state`. Two independent signals, and the one that gates the arm is the one that observes the room.

**Keep the generated line.** `ModalRunLine.tsx` and `modalCommand.ts` stay, collapsed under "Run it yourself instead", with the i18n prose changed from *"run this in the other terminal"* to *"what the Lab will run — copy it if you'd rather launch by hand"*. It earns its place three ways: it is the only route when `modal` is missing or unauthenticated; it is the only route to `--detach` or a hand-tuned `--slack`/`--rtc-schedule`; and it is the **ground truth** an operator compares against when the fingerprint watchdog fires. Two invariants must survive: the command text is **DATA** (never localized — `modalCommand.ts`'s docstring is emphatic), and the API **still never returns the API secret** (`LOCAL_SECRET_PLACEHOLDER` stays; the Lab-launched path gets the secret from the key file into the child env, never through a response body).

### Invalidated-by-S3.6 list

Ordered by how much they'd cost to miss:

1. **`modalCommand.ts`'s `source === "local_override"` branch** — emits `--tailscale`, `--livekit-url`, and the two placeholders. 2. **`--sfu-external-ip` may delete tailscale entirely.** If the Lab SFU advertises its STUN-discovered public IP and a Modal container can hole-punch to it, the `--tailscale` path is dead weight for the Lab-launched case. That is an *empirical* question about the user's NAT, not a design one — see open question #2.
3. **`LOCAL_SFU_CONFIG_PATH = "~/.cache/huggingface/lerobot/livekit.local.yaml"`** — confirmed stale-in-waiting: S3.6's worktree defines `LIVEKIT_CONFIG_FILE` = `livekit_config.yaml` and `LIVEKIT_KEY_FILE` = `livekit_keys.yaml`. The placeholder prose ("read the secret from …") points at a file that will not exist.
4. **`POST /api/v1/remote-inference/clear-local-override`** and its button in `TransportSection.tsx` / `RemoteInferenceStatusPanel.tsx` — likely retired with the override, taking a `V1_ONLY_ROUTES` entry and `handle_clear_local_override` with it.

7. **`TransportSection.tsx`'s whole shape** — `sfu_config_exists` / `local_env_exists` / `local_env_path` in `RemoteInferenceTransportStatusResponse` are override-specific fields.

## 7. Risks, open questions, checklist

### Risks

- **Three guaranteed merge conflicts with S3.6**, all trivial but all in equality-asserted files: `tests/test_api_errors.py::DOMAINS`, `tests/test_api_contract.py::V1_ONLY_ROUTES`, and `docs/api/openapi.json`. The last must be resolved by **regenerating after the merge**, never by hand-merging the snapshot.
- **`pyproject.toml` and `uv.lock` are currently `UU` in `wt-s36`.** Whatever S3.8 branches from should branch after that is settled — and S3.8 adds no dependency, so it should not touch either file at all.
- **Two new level-1 error domains in one week** (`sfu`, `gpu`). See open question #1.
- **The wrapper edit is duplicated by design.** Both wrappers carry *"Fix bugs in both, or factor into a `_tailscale.py`"*. Keep the six lines byte-identical; do not opportunistically factor (there is genuinely no shared import path into both images).
- **Ambient `LIVEKIT_API_*` in an operator's shell** now reaches the container for hand-run `modal run` invocations. Scoped to credentials only (§1c); the room/url decision stays flag-only.
- **`ready` is a log-derived hint, not a fact.** If Modal ever reformats or buffers container stdout differently, the parser degrades to "never reaches ready" — which shows as a cold-start timeout on a run that is actually healthy. The mitigation is that the *arm-facing* gate is `_probe_room`, which is unaffected; the worst case is a misleading panel, not a wrong energization.
- **`modal` client version drift.** 1.4.3 here; a future client could change `modal run`'s flags. The launcher shells out with a stable, small flag set (`run`, a path, `--flag value`) — the surface most likely to survive.

### Open questions for the coordinator

1. **`gpu.*` as a new domain, fold into S3.6's `sfu.*`, or `system.*`?** I REC `gpu.*` on the taxonomy's own reasoning, but two new domains in one week is a call above this plan.
2. **Does `--sfu-external-ip` remove the need for `--tailscale` on the Modal side?** If yes, the launcher's argv and `modalCommand.ts`'s local branch both shrink to nothing. This needs a live hole-punch test through the actual NAT, not a design decision. Until it is answered, `TransportPlan.needs_tailscale` is the seam.
3. **Attached-only in S3.8, or ship `detach` from day one?** I REC attached-only; `--detach` brings orphan-cost and reattach-by-id and buys little for a GPU started a minute before a run.
4. **Should `gpu/start` refuse while `jobs.training_is_active()`?** I REC **no** — a Modal A100 is not this machine's GPU, and CLAUDE.md already flags the existing remote-inference↔training refusal as *"the one asymmetry in the matrix, deliberate and revisitable"*. Adding a second, weaker instance of it would entrench a rule we already suspect.
5. **Idle auto-stop default: 10 minutes.** Confirm, or name a number.
6. **After S3.6, where do the key/secret/url/room come from —** `sfu.api_keys()`+`sfu.sfu_url()`+`sfu.default_room()`, or a successor to `_read_env()`? One answer, consumed by both the session's preflight and the launcher.
7. **Does the coordinator want `app_url` at all in S3.8?** It is display-only and its parse format is unverified; dropping it removes the one field I could not confirm without running `modal`.
