## 1. The fork's MolmoAct2 contract for the RTC policy server

**Registration** — `.venv/.../lerobot/policies/molmoact2/configuration_molmoact2.py:31`:
```
@PreTrainedConfig.register_subclass("molmoact2")
@dataclass
class MolmoAct2Config(PreTrainedConfig):
```
Policy class `MolmoAct2Policy` (`modeling_molmoact2.py:511`), `config_class = MolmoAct2Config`, `name = "molmoact2"`. `get_policy_class("molmoact2")` resolves it — no Lab-side registration needed.

**The `molmoact2` extra** (installed `lerobot-0.6.2.dist-info/METADATA:183-185`) is three dep groups:
- `transformers>=5.4.0,<5.6.0`
- `peft>=0.18.0,<1.0.0`
- `scipy>=1.14.0,<2.0.0`

No torch/CUDA pin of its own — torch comes from lerobot core, so the extra imposes **no new CUDA constraint**. transformers 5.4–5.6 is the only tight one.

**Config fields that matter at inference:**

| field | default | published ckpt |
|---|---|---|
| `checkpoint_path` | `"allenai/MolmoAct2"` | `"allenai/MolmoAct2-SO100_101"` |
| `inference_action_mode` | `None` | `"continuous"` |
| `action_mode` | `"both"` | `"continuous"` |
| `model_dtype` | `"bfloat16"` | **`"float32"`** |
| `enable_lora_vlm` | `False` | `False` |
| `rtc_config` | `None` | `null` |
| `expected_max_action_dim` | `32` (validated == 32) | 32 |

**`inference_action_mode` is not optional.** `_resolve_inference_action_mode` (`modeling_molmoact2.py:267`) raises on `None`:
> `"MolmoAct2 inference requires 'inference_action_mode' to be set explicitly to either 'continuous' or 'discrete'."`

**`supports_rtc()` exists and is exactly one predicate** (`modeling_molmoact2.py:523`):
```python
def supports_rtc(self) -> bool:
    return self.config.inference_action_mode == "continuous"
```

**The RTC call shape policy_rtc.py needs is present.** `predict_action_chunk(self, batch, **kwargs)` (L1640) reads `inference_delay`, `prev_chunk_left_over`, `execution_horizon`, `num_steps`, `generator` and dispatches to `_generate_actions_from_inputs_with_rtc` (L1462) when `self._rtc_enabled()` — which is `config.rtc_config is not None and config.rtc_config.enabled`, i.e. exactly what `enable_rtc()` sets. The guided loop calls `self.rtc_processor.denoise_step(x_t=…, prev_chunk_left_over=…, inference_delay=…, time=…, execution_horizon=…)` — the same `RTCProcessor` the Lab already drives for smolvla/pi05. **The Lab's RTC path works on MolmoAct2 unchanged.**

**Return shape is already unpadded**: `return actions[:, : self.config.n_action_steps, :action_dim]` where `action_dim = _output_action_dim(batch)` reads `config.output_features["action"].shape[0]`. So you get `(1, 30, 6)`, not the 32-wide internal dim. `select_action` is unusable under RTC by design — it raises `AssertionError("RTC is not supported for select_action, use it with predict_action_chunk")`. policy_rtc.py already only calls `predict_action_chunk`.

**`policy_wire_schema` (`drtc/_schema.py`) derives correctly — but only because the checkpoint is complete.** It reads `cfg.robot_state_feature` / `cfg.action_feature` / `cfg.image_features`. The trap: `MolmoAct2Config.validate_features()` (called in `__init__`) **injects** `observation.state` shape `(0,)` and `action` shape `(32,)` when they are absent. A checkpoint missing `output_features` would therefore silently produce a 32-wide action schema and a 0-wide state schema — Portal fingerprint mismatch, packets silently dropped, "0 chunks". The published checkpoint has both, so it derives `state_dim=6, action_dim=6, cameras=["cam0","cam1"]`.

**Two gaps in the Lab's own code:**

1. `enable_rtc()` (`policy_rtc.py:127`) decides support by `has_hook and hasattr(cfg, "rtc_config")` and **never calls `supports_rtc()`**. MolmoAct2 passes that test unconditionally. On a `discrete` checkpoint it would report `RTC ENABLED` and then raise `ValueError("RTC is only supported for continuous MolmoAct2 inference.")` on *every* inference, instead of degrading to plain chunks the way the ACT branch does.
2. **The task string is silently optional and shouldn't be.** policy_rtc.py sets `batch["task"]` only `if self.task`. MolmoAct2's `_as_text_list(None, 1)` returns `[""]` (`processor_molmoact2.py:381`), producing the prompt `"The task is to . The setup is …"`. No error, just a degraded VLM. `--task` is effectively mandatory.

## 4. Cost/risk of the GPU-image pin change

**First, a correction to the brief: upstream `8414188d` does *not* predate MolmoAct2.** It ships `src/lerobot/policies/molmoact2/` with a `configuration_molmoact2.py` whose field set is byte-identical to the fork's. The actual reason the image must move is different and stronger: **upstream `8414188d` is lerobot `0.5.2` and has no `supports_rtc` anywhere in the tree** (`grep -rn "def supports_rtc" $UPSTREAM/src/lerobot/` → zero hits; the fork has 7 plus `rollout/inference/rtc.py:66 supports_rtc_inference`). The fork is `0.6.2`. So the image bump is a **0.5.2 → 0.6.2 minor-version jump plus the makermods arm work**, not a MolmoAct2 availability fix.

**Fork-internal drift is nil.** `b968c0c01..eaab69339` is exactly two commits:
```
eaab6933 Merge arm/makermods-metal: leader-frame unwrap window fix
85a3000d fix(rebot_102_leader): unwrap raw angles in leader-frame degrees
```
touching 3 files / 59 insertions, all `rebot_102_leader` (config, driver, its test). **Nothing in policies, processors, or the factory.** So everything I read from the installed b968c0c01 venv is authoritative for eaab69339.

**What could break for existing SmolVLA/ACT paths on 0.5.2 → 0.6.2** (diffed offline from `~/.cache/uv/git-v0/checkouts/`, both refs present — no fetching):

*Verified safe:*
- `make_pre_post_processors(policy_cfg, pretrained_path=…, preprocessor_overrides=…, postprocessor_overrides=…)` — signature identical in both.
- `lerobot/policies/rtc/configuration_rtc.py` — **byte-identical** (`diff` empty). `RTCConfig(enabled, prefix_attention_schedule, max_guidance_weight, execution_horizon)` unchanged.
- `RTCAttentionSchedule` exported from `lerobot.configs` in both.
- `predict_action_chunk` / `select_action` present with the same call shape on `act`, `smolvla`, `pi05` in both.
- `lerobot/policies/rtc/` file list identical.

*Real drift, worth watching:*
- **`lerobot.types` → `lerobot.lerobot_types` module rename.** No `makermodslab/**` file imports either (grep clean), so the Lab is unaffected — but any third-party or vendored code in the image that does will break.
- **`get_policy_class` changed from a hardcoded if/elif chain to convention-based resolution** (looks up the draccus-registered config class, rewrites `configuration_*` → `modeling_*`). Behaviourally equivalent for registered types and *more* permissive, and it now raises `ValueError`/`ImportError` where 0.5.2 raised `NotImplementedError`. `policy.py:61` and `policy_rtc.py:182` both call it and neither catches those, so an unknown type surfaces as a different exception class — cosmetic in the logs, not a crash-behaviour change.
- **`peft` moved from function-local imports to a module-level `_peft_available` guard** in `modeling_molmoact2.py`. Harmless with the `molmoact2` extra installed.
- The fork adds policies upstream 0.5.2 lacks (`evo1`, `fastwam`, `lingbot_va`, `common/`). Additive.

**Per CLAUDE.md this is a real lerobot bump and needs an end-to-end run** — but the blast radius is narrower than the version numbers suggest: the four API surfaces the two policy servers actually touch (`PreTrainedConfig.from_pretrained`, `get_policy_class`, `make_pre_post_processors`, `predict_action_chunk`) are unchanged in shape. **The regression I'd actually watch for is behavioural, not structural:** a smolvla or pi05 checkpoint trained under 0.6.x processor semantics running against a 0.5.2 processor pipeline (or vice versa) — the same class of "config compatibility follows the lerobot that WROTE the checkpoint" hazard the existing image comment warns about for PI05Config. Re-run one known-good smolvla RTC session on the new image before declaring it.

## 5. Acceptance test

Preconditions: `remoteRunConfig.ts` has `molmoact2` in `FLOW_POLICY_TYPES`; the camera-binding problem (§3c) is resolved; the image is rebuilt on the fork pin.

```
modal run makermodslab/drtc/modal_policy_rtc.py \
  --policy-path lerobot/MolmoAct2-SO100_101-LeRobot \
  --task "pick up the block and put it in the box" \
  --horizon 30 \
  --fps 30 \
  --s-min 4 \
  --video-codec H264 \
  --livekit-room <room from the Lab panel>
```

`--horizon 30` (not the `DEFAULT_HORIZON.rtc` 50) — it is the checkpoint's `n_action_steps`, and a longer declared horizon breaks the Portal chunk fingerprint. `--task` is free-text and mandatory: the checkpoint carries no task string and no `train_config.json`, and the prompt template is `"The task is to {task}."`, so phrase it as an infinitive-completion.

**What to watch, in order:**
1. `[policy] >>> policy_rtc build marker: bg-claim-v2 …` — if absent, Modal shipped a stale mount and nothing below is meaningful.
2. `[policy] RTC ENABLED: schedule=LINEAR max_guidance_weight=10.0 execution_horizon=26` — `26` = `30 − 4`. `RTC FAILED to enable` or the `has no RTC support` warning means `inference_action_mode` didn't survive the load.
3. **GPU memory.** With `model_dtype: "float32"` on a 40 GB A100 this is the most likely first failure. If it OOMs, that is the expected outcome, not a mystery — move to `A100-80GB` or override the dtype.
4. Non-zero chunk *and* observation counts. Zero-on-both-sides with a healthy transport is the Portal fingerprint mismatch signature — check state_dim 6+5 RTC fields and camera track names `cam0`/`cam1`.
5. Steady-state inference latency. fp32 7B at 30 Hz will not keep up; expect the robot's latency estimator to report a large `d` and RTC to be doing heavy in-painting.

**Cold start:** first run downloads **21.78 GB** (`allenai/MolmoAct2-SO100_101`, 5 safetensors shards) into the `hf-cache` volume at `/cache/huggingface`, plus the ~14 GB LeRobot wrapper's own `model.safetensors`. Budget **several minutes before the first log line past model load**, and note the download starts *before* `_load_hf_model` because `_apply_norm_tag_metadata` snapshot-downloads the repo just to read a 4.8 KB `norm_stats.json`. Subsequent runs hit the volume. The image build itself adds only ~40 MB (peft + scipy).
